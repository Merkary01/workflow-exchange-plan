Workflow Exchange

A shared second memory for two AI-team setups. Each of us keeps our own workflow; the exchange lets us compare them, see what the other has learned, and borrow what's useful without merging anything.

Shelton · Unreal Engine Partner · Godot Shared: how to run an AI team well

Why this is worth building

We both run a team of AIs through the same kind of setup: a lead AI, several helper AIs, a task board, shared memory, skills, and a local dashboard (WorkFlowHQ on Shelton's side). Our projects are different, but most of what makes the team work is not engine-specific: how tasks are sized and routed, which model is worth its cost, which checks catch bugs before a compile, what went wrong and how it was fixed.

Today that knowledge stays on each PC. When one of us learns something the hard way (for example, that a model benchmark run in parallel ate 15% of a paid usage window), the other has to learn it again. The exchange fixes that.

Both setups started from the same AI team kit, so the folders and file formats already match. Comparing them is mostly a matter of lining up files, not translating between systems.

What travels, and what never does

Shared (know-how)

  • Skills: the instruction files that make the AIs good at a job (.claude/skills/*).
  • Measured lessons from shared memory: what was tried, what was measured, what changed.
  • Model results: which model won on which kind of task, at what cost.
  • Workflow rules and the reason behind each one.
  • Tools and scripts that aren't tied to one project (routing, wake-ups, the dashboard).

Never shared

  • Project source code and game assets.
  • Logins, tokens, API keys, account emails, session IDs.
  • Chat history and task transcripts.
  • Anything outside the curated pack: the exchange can't read your PC, only what you publish.

How it works

  1. Publish a pack. A command (and a button in the dashboard) collects the shareable files from your setup, removes anything that looks like a secret, shows you the list, and only publishes after you confirm. Each pack is a dated snapshot.
  2. The exchange repo holds both packs. One small private GitHub repo that only the two of you can access. Each person writes only to their own folder.
  3. Compare. A Compare tab lines up the two packs: skills one side has and the other doesn't, rules that differ on the same topic, and each side's measured lessons, filterable by domain.
  4. Import into peer memory. You pick items to bring over. They land in a separate peer memory layer, labeled with where they came from. Your AIs can read it as advice.
  5. Promote what proves itself. When a borrowed skill or rule works for you, you promote it into your own workflow. That step always needs your approval.

What a pack looks like

A plain folder of text files, so it's easy to read, diff and review on GitHub:

workflow-exchange/
  shelton/                       # only Shelton writes here
    pack.json                    # date, domains, kit version, item list
    skills/
      team-health/SKILL.md       # general
      ue-build/SKILL.md          # unreal
    lessons.md                   # measured lessons, one per line, with date and domain
    models.md                    # model results: task, models, winner, cost
    rules.md                     # workflow rules and their reasons
    tools/                       # portable scripts, if chosen
  partner/                       # only the partner writes here
    ...

Every item carries a general, unreal or godot label, so the Compare tab can show "general" lessons first and keep engine-specific ones out of the way until you want them.

The rules for peer memory

  • Advice, never orders. Your own rules always win. A borrowed item can inform an AI's work but never overrides CLAUDE.md, your skills, or your decisions.
  • Always labeled. Every peer item shows who it came from and when, so nobody mistakes it for a rule of yours.
  • Measured beats claimed. Items that record a measurement ("took 72 s", "used 719k tokens") are marked as measured; opinions are marked as opinions.
  • Easy to drop. Removing an imported item is one click and leaves no trace in your own workflow.

Privacy and safety

RiskHow the design handles it
A token or key slips into a packThe pack builder scans for key-like strings, emails and account IDs and refuses to publish until they're removed. You review the full list before anything leaves the PC.
Someone else reads the exchangeA private GitHub repo with exactly two members. Nothing is public.
One side overwrites the otherEach person writes only their own folder; the exchange tool refuses to write the other one.
A borrowed rule breaks a workflowImports land in peer memory as advice. Nothing reaches your real workflow without a promote step you approve.
Hidden behavior in shared scriptsScripts are plain text, reviewed on GitHub before import, and never run automatically after an import.

Build plan

Four tasks, built by the AI team the usual way (plan, build, review, test). Each one is usable on its own.

TaskWhat it deliversSize
1. Pack builderA command that gathers skills, lessons, model results and rules into a pack, labels domains, scans for secrets, and shows the list for approval.M
2. Exchange repo + publishThe private repo layout, publish and pull commands, and the "write only your own folder" guard.S
3. Compare tabA WorkFlowHQ tab: skills side by side, differing rules, lessons by domain, a diff view for any file.M
4. Peer memoryImport into a labeled advice layer the AIs can read, one-click removal, and a promote step with approval.M

The partner's dashboard may differ from WorkFlowHQ. Tasks 1, 2 and 4 are plain files and commands that work on any kit-based setup; task 3 is the only dashboard-specific part, and the same Compare view can be added to the partner's side later.

Decisions for the two of you

Who owns the exchange repo?Either account can create it and invite the other. The owner can't read anything the other didn't publish.
How often do packs publish?Manual only (recommended to start), or on a schedule with a review prompt.
Which domains count as "general"?Suggested: team workflow, model choice and cost, review and testing habits, tooling. Engine topics stay labeled by engine.
Can AIs read peer memory on their own?Only the lead AI (recommended), or every AI on the team, or nobody until you import by hand.
Are scripts shared, or only knowledge?Knowledge only to start is the safer choice; scripts can be added once you both trust the flow.
